# 网页验收问题与待确认修复方案

记录日期：2026-10-11。状态：只读排查完成；本轮按用户最新约束更新实施方案，尚未实施源码修复或整合安装包。

## 用户确认的路由范围

继续使用当前唯一 12 节点 LangGraph，不恢复旧执行模式，不增加工作流节点。

| 现有路径 | 给模型的能力清单 | 本次修改范围 |
| --- | --- | --- |
| Chat | 不发送能力清单 | 路由和聊天流程保持原样 |
| Direct Action / app_executor | 当前启用的 App Action：用途、参数 schema、前置条件、权限、确认策略 | 增加一次语义匹配，生成已校验的 AppIntent 后沿用现有执行器 |
| 简单任务 / fast_react | 此路径实际允许调用的工具及其规则 | 保留现有流程；读取规则时明确要求结合用户语义匹配工具 |
| 复杂任务 / planner | 此路径实际允许调用的工具、Skill、MCP、SubAgent 及其规则 | 保留现有规划、执行、验证；能力发现时做语义匹配 |

清单直接从当前 Registry 与实际允许的工具生成，禁止维护一份脱离真实执行器的手写清单。
简单任务和复杂任务复用现有 capability_discovery 的模型调用，避免再增加独立往返。
Direct Action 只解析一次；匹配结果传给执行器，执行器不再次按原句解析或另调模型兜底。
模型不授予权限、不批准确认、不虚构对象 ID；必要时通过既有只读查询解析对象，歧义时澄清。
明确任务不能因为规则没覆盖某个中文词就被阻断；否定、解释和引用中的命令不应触发写入。

## 已确认问题

1. 模型配置共用一个 `XILIU_API_KEY`。保存另一厂商的密钥会覆盖当前值。
   前端切换厂商也不清除 API Key 输入草稿，已配置状态没有按厂商区分。
2. DeepSeek reasoning_content 有专门的流事件适配；OpenAI 没有对应推理摘要适配。
   Planner 等提示词主要为英文，没有统一中文展示约束。
3. `把文字「构建个人知识库的灵感」存入 Inbox。` 在无模型调用的规则解析中被判为 clarify：
   import 规则未包含“存入”。真实会话又在结构化模型解析中失败，被统一包装为不明确请求。
4. 两次链接导入有 ok=true、verification.passed=true 的真实 App 回执。
   回执 status=inbox，后台随后改为 knowledge；InboxService._finish 会按标签选择文件夹并自动归类。
   Verifier 重查导入瞬间的记录快照，报 App receipt no longer matches persisted state。
   这既涉及后台并发与回执生命周期，也涉及“仅存 Inbox”是否允许自动归类的语义。
5. `建立研究数据库` 的现有 trace 显示三次 todo_update 都失败：
   `todo must be in_progress before completed`。模型把 pending 直接改成 completed。
   执行器遇到首个错误便结束本轮，外层重新规划后重复错误；最终只显示笼统预算/工具失败。

## 拟实施顺序与验收条件

### A. 独立模型配置

- 引入 profile_id 与配置集合：至少 OpenAI、DeepSeek 各自保存密钥、Base URL、选中模型；
  同厂商自定义模型可有独立 profile，助手会话明确引用 profile，防止跨厂商残留 model_override。
- 切换只选择配置，编辑和保存仅影响该配置；密钥不返回浏览器。
  页面按当前配置显示“已配置”，切换时隔离输入草稿。
- 旧单份配置迁移到当前对应厂商。已被覆盖的旧密钥无法从现存值恢复，需用户重新填写一次。
- 验收：OpenAI→DeepSeek→OpenAI 往返，密钥/地址/模型不串用；保存空值保留当前配置密钥。

### B. 中文执行过程与 provider 适配

- 应用阶段、工具错误、最终结果统一中文。模型提示词明确中文输出。
- DeepSeek 已返回的 reasoning 数据继续正确处理；界面默认展示依据真实事件生成的中文执行摘要。
  对英文 provider 内容提供中文摘要，不保证原始推理本身始终为中文，也不伪造模型推理。
- 对支持推理摘要的 OpenAI 模型适配 Responses API 的 reasoning summary 流，并保持工具轮次、
  取消和上下文兼容；不支持摘要的模型准确标明，只展示真实执行步骤。
- 验收：分开测试执行步骤、provider 摘要、无摘要三种情况，结果不能混入正文或丢失。

### C. 语义匹配与真实执行失败

- Direct Action 按上述范围引入基于完整 Action 规则的语义匹配，不逐词追加中文命令正则。
  规则提供候选与安全约束，模型依据用户输入输出结构化 Action 和参数；执行器核验 schema、
  真实对象、权限与确认。简单/复杂路径在读取各自规则时进行同样语义匹配，保留原执行流程。
  模型结构化解析失败按格式、鉴权、超时等分类，不再全部称为意图不明确。
- 将仅保存 Inbox 与自动归档的意图分开，后台不自行超出用户指定目的地。
  UI 原有自动整理能力保留；助手明确要求仅存 Inbox 时，不隐式自动归档。
  采用 Action 专属后置条件：核对内容、来源、目标和真实任务状态；区分已保存、处理中、处理失败。
  保留版本冲突、内容丢失、错误归档等检查，不删除验证器或降低数据库断言。
- 保留 todo 状态约束。将可纠正参数/状态错误的具体回执反馈给当前模型，在有限轮次内修正；
  不重新执行成功写入，权限拒绝、确认请求和非幂等错误仍停止。
- 最终中文错误显示具体失败工具、原因和已完成部分；trace 不把正常结束错误标为 interrupted。
- 验收：截图三类场景及后台竞态、人工修改冲突、重复写入、权限拒绝都使用真实服务回归。

### D. 真实模型验收后再打包

- 先运行确定性回归和网页重现场景，再在隔离数据库/工作区运行原 51 条真实模型任务。
  按已配置、用户选择的 OpenAI/DeepSeek profile 验证，明确记录鉴权/配额/不可用模型阻塞。
- 逐条记录实际节点路径、工具参数与回执、数据库/文件效果、耗时及结果；
  单独报告测试通过数、真实完成数、合理澄清/确认数与实际失败数。
- 不调整期望来容忍可完成任务失败，不自动批准删除确认，不改动用户实际资料。
- 用户网页确认后才整合安装包；本次未启动任何新付费模型调用。

## 多语义测试计划

1. 每个代表性意图使用 6–10 个表达变体，覆盖文字保存、链接保存、待办创建/查看/完成、
   知识库检索、文件夹创建和资料整理；例如“存入”“帮我收着”“记到收件箱”“先放 Inbox”。
   不把这些变体复制进生产正则作为修复方式。
2. 加入负向表达：“不要保存”“解释如何保存”“如果我删除会怎样”，以及引用文本包含命令。
   对照断言只读/解释、零写入，防止语义匹配误执行。
3. 加入明确对象、同名对象、缺少内容、缺少时间、相对日期、多步骤复合请求和上下文指代。
   能执行的检查具体效果；确实缺少信息的检查明确澄清，不以提高完成率为由猜测。
4. 逐路径验证发送的真实清单：Chat 无清单；Direct 仅 App Action；Fast 和 Planner 均只能
   使用本路径 Policy 允许的能力，未授权工具即使模型选择也必须拒绝。
5. 在真实 Inbox worker 运行期间验证导入，覆盖后台分类、元数据更新、人工并发修改、
   服务失败和重放，断言原文不丢、目的地正确、不重复写入。
6. 用模型返回 pending→completed 错误调用的场景复现当前 Planner 问题，要求具体反馈、
   合法状态修正、保留成功步骤；权限拒绝不能进入纠错后绕过。
7. 模型配置切换测试覆盖 OpenAI→DeepSeek→OpenAI、空密钥保存、不同 Base URL、会话模型
   残留和切换未保存输入；既有密钥只能用于其所属配置，密钥不能出现在 API 回包或日志中。
8. 测试分开记录：确定性回归、真实模型多语义成功率、原 51 条真实模型测评、网页人工验收。
   不把模拟模型成功率当成真实模型成功率，也不把合理澄清和确认计为业务执行完成。

建议实施顺序：配置隔离 → Direct 语义匹配与路径清单 → Inbox/Planner 失败修复 →
中文过程与 provider 摘要适配 → 多语义和真实模型验收 → 网页确认 → 安装包整合。
